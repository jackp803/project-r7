# Canonical Funding Allocation Evidence Profile — V0.1

> Parent contract set: `contracts-v0.1`  
> Profile identifier: `funding-allocation-v0.1`  
> Profile status: `BASELINE`  
> Technical authority: E7 Integration / Architecture / System QA / Release Engineer  
> Decision task: `E7-20260824-041`

## 1. Purpose

`trade-result-v0.1` already requires final funding to be either explicitly included or explicitly confirmed zero. The accepted financial meaning is already fixed:

```text
positive funding_cost = cost
negative funding_cost = credit
net_pnl = gross_pnl - total_fees - funding_cost_effective
```

The missing boundary is not the PnL formula. It is the governed cross-module evidence object that proves what funding applies to one exact closed Position interval.

Before this profile, E5 had an internal `FundingEvidence` validation helper, but that helper is explicitly not a shared or persisted contract. E4/E6 therefore cannot lawfully import or recreate that private shape as a cross-module interface.

This profile defines one immutable provider-neutral `FundingAllocationEvidence` object that:

```text
E4 funding source truth / Paper funding model
-> canonical FundingAllocationEvidence
-> E5 validation + trade-result-v0.1 finalization
-> E6 immutable persistence / replay / audit
```

It does not authorize provider/private API access, credentials, PAPER, SHADOW, LIVE, or release-gate advancement.

## 2. Versioning and compatibility decision

Classification:

```text
ADDITIVE_PROFILE_REQUIRED
```

The parent remains:

```text
schema_version = contracts-v0.1
```

No set-wide major version bump is required because:

1. `contracts-v0.1` never defined a serialized FundingAllocationEvidence object;
2. `trade-result-v0.1` already requires explicit/versioned funding evidence but did not define the cross-module evidence shape;
3. the new object/profile and TradeResult audit references are additive;
4. existing entry, protection, close, quantity, fee and PnL meanings are not reinterpreted;
5. historical/static TradeResult objects without this profile remain valid for their original purpose, but are not eligible as current Gate B final TradeResult evidence once the new producer/consumer path is adopted;
6. no historical object may be rewritten to claim evidence that was not actually produced.

Legacy E5 `FundingEvidence` is an internal implementation helper only. It is not upgraded into a shared object by name or by convention. A later E5 implementation must consume this shared profile explicitly.

## 3. Shared object name and required serialized fields

Canonical shared object:

```text
FundingAllocationEvidence
```

Required fields for `funding-allocation-v0.1`:

- `schema_version` — exactly `contracts-v0.1`
- `funding_evidence_profile_version` — exactly `funding-allocation-v0.1`
- `funding_evidence_id` — stable content-derived identity defined in section 10
- `source_kind` — `PAPER_MODEL | BROKER_LEDGER`
- `source` — non-empty provider-neutral logical source identifier
- `source_version` — non-empty immutable semantics/version identifier for the source adapter/model
- `source_material_hash` — stable SHA-256 content hash of the normalized authoritative source material used for this allocation
- `source_record_count` — non-negative integer count of applicable normalized source records
- `source_complete_through` — RFC 3339 UTC completeness watermark proving the source is authoritative through at least `interval_end`
- `trade_plan_id` — exact parent ApprovedTradePlan lineage for this one position instance
- `position_id` — exact canonical Position identity
- `symbol` — canonical instrument symbol
- `interval_start` — exact authoritative TradeResult `opened_at`
- `interval_end` — exact authoritative TradeResult `closed_at / flat_position_observed_at`
- `interval_semantics` — exactly `START_INCLUSIVE_END_EXCLUSIVE`
- `status` — exactly `ZERO_CONFIRMED | INCLUDED`
- `funding_cost` — finite signed base-10 decimal string; rules in section 7
- `cost_currency` — current V0.1 value exactly `USDT`
- `calculated_at` — RFC 3339 UTC timestamp when the canonical allocation evidence was calculated/materialized

Provider-native account IDs, API credentials, request signatures, exchange tokens, raw secrets, withdrawal/funding-transfer authority and live-mode authority are forbidden.

### 3.1 Source-kind meaning

`PAPER_MODEL` means funding truth is generated by an explicit local versioned Paper funding model owned by E4. It is not evidence from a real provider account.

`BROKER_LEDGER` means the producer normalized authoritative broker/account funding ledger truth. Provider-specific transport and raw fields remain inside E4/provider adapters and are not part of this shared profile.

`BROKER_LEDGER` does not itself authorize private/provider access. Such access requires a later release stage and explicit authorization.

## 4. Required lineage and intentionally omitted lineage

Required exact binding is:

```text
trade_plan_id
position_id
symbol
interval_start
interval_end
```

`position_id` is the primary one-position allocation identity. `trade_plan_id` is also required so funding cannot be substituted across plans merely because a position-shaped object is malformed or reused. `symbol` prevents cross-instrument allocation.

The following are intentionally **not** required fields on FundingAllocationEvidence:

```text
risk_decision_id
risk_policy_version
strategy_id
strategy_version
```

Reason: funding allocation is execution/account/Paper-source truth, not risk or strategy authority. Requiring the funding source to manufacture E5 risk/strategy lineage would invert ownership. E5 already validates the exact parent ApprovedTradePlan when producing TradeResult, and the final TradeResult retains risk/strategy lineage independently.

A future product model supporting multiple position instances under one `position_id`, which is currently forbidden, would require a new contract review.

## 5. Exact interval and boundary semantics

For `trade-result-v0.1`:

```text
interval_start = authoritative opened_at
interval_end   = authoritative closed_at = flat_position_observed_at
```

The canonical funding allocation interval is half-open:

```text
[interval_start, interval_end)
```

Serialized enum:

```text
interval_semantics = START_INCLUSIVE_END_EXCLUSIVE
```

Rules:

- `interval_start < interval_end` is required;
- a normalized funding event with `event_time == interval_start` belongs to this position interval;
- a normalized funding event with `event_time == interval_end` does not belong to this interval;
- adjacent positions whose prior `interval_end` equals the next `interval_start` therefore cannot both allocate the same boundary event;
- the source adapter/model must normalize provider/model event time sufficiently to apply this rule deterministically;
- if provider/source semantics cannot prove which interval owns a boundary event, final canonical evidence must not be emitted and TradeResult finalization remains blocked.

Overlapping, wider, narrower, approximate or inferred intervals are not accepted as final evidence in V0.1. The evidence interval must exactly equal the final TradeResult position interval.

## 6. Completeness and final-evidence semantics

`funding-allocation-v0.1` represents only **finalizable canonical funding evidence**.

Allowed `status` values are exactly:

```text
ZERO_CONFIRMED
INCLUDED
```

There is deliberately no final shared `UNKNOWN`, `PARTIAL`, `INCOMPLETE` or `UNAVAILABLE` value in this profile.

If a source is unavailable, incomplete, stale, ambiguous or unsupported, the producer may retain domain-local diagnostic state, but it must **not** emit a valid final FundingAllocationEvidence object. E5 must treat absence of valid canonical evidence as a TradeResult finalization blocker.

### 6.1 Source completeness watermark

A final object requires:

```text
source_complete_through >= interval_end
calculated_at >= interval_end
```

`source_complete_through` is a source-owned assertion that all applicable funding facts through that point are available under `source_version` semantics.

A query returning zero rows without a completeness guarantee is not sufficient.

### 6.2 `ZERO_CONFIRMED`

`ZERO_CONFIRMED` means the authoritative source/model proves **no applicable funding allocation records exist** for the exact canonical interval.

Required invariants:

```text
status = ZERO_CONFIRMED
source_record_count = 0
funding_cost = "0"
cost_currency = "USDT"
source_complete_through >= interval_end
```

A missing row, failed query, timeout, unknown provider state, partial page, incomplete cache, or unversioned model default can never authorize `ZERO_CONFIRMED`.

### 6.3 `INCLUDED`

`INCLUDED` means one or more authoritative funding records apply to the exact interval and were deterministically aggregated.

Required invariants:

```text
status = INCLUDED
source_record_count >= 1
funding_cost = finite signed decimal string
cost_currency = "USDT"
source_complete_through >= interval_end
```

`INCLUDED` may legitimately have `funding_cost = "0"` when one or more included records net exactly to zero. That case remains `INCLUDED`, not `ZERO_CONFIRMED`.

## 7. Signed cost and currency semantics

Funding follows the already accepted cost-sign convention:

```text
positive funding_cost = cost
negative funding_cost = credit
zero funding_cost     = zero net funding
```

`funding_cost` is always serialized as a base-10 decimal string and must be finite.

For current:

```text
pnl_profile_version = linear-base-asset-pnl-v0.1
pnl_currency = USDT
```

this profile requires:

```text
cost_currency = USDT
```

No currency conversion is defined by V0.1. Evidence denominated in BTC, another quote currency, points, contracts, or an unknown currency is not compatible with current TradeResult finalization and must fail closed.

A future conversion profile requires separate E7 review/versioning.

---

## 8. Source-material normalization and aggregation

The source owner must normalize all applicable funding source records under one immutable `source_version` semantic before producing evidence.

For `INCLUDED`:

1. select only records whose normalized event time belongs to `[interval_start, interval_end)`;
2. reject duplicate source records under the source-version identity rule;
3. order normalized records deterministically using the source-version stable record identity and event time;
4. normalize every applicable signed cost into `USDT` before V0.1 evidence is allowed;
5. sum with Decimal arithmetic;
6. set `source_record_count` to the number of included normalized records;
7. compute `source_material_hash` from the complete normalized ordered source material plus completeness assertion used for the allocation.

For `ZERO_CONFIRMED`, `source_material_hash` must hash the explicit complete zero-confirmation material: source/version, exact interval/lineage and the source/model completeness assertion. It must not be a hash of an accidental empty API response alone.

The precise raw provider record schema is intentionally not standardized here. Provider-native fields remain E4 adapter/audit facts. `source_version` owns their normalization semantics.

## 9. Paper-mode source semantics without provider credentials

V0.1 allows a legitimate Paper-mode producer without provider credentials or private APIs.

E4 may implement a versioned local Paper funding source/model. Examples of valid source versions include conceptually:

```text
paper-zero-funding-v0.1
paper-scheduled-funding-v0.1
```

Names are illustrative; implementation chooses exact registered version strings.

### 9.1 Paper zero model

A Paper model may emit `ZERO_CONFIRMED` only if its declared version semantics explicitly state that no funding accrual is applied for the complete requested interval.

This is a positive model assertion:

```text
versioned Paper policy says funding = 0 for all instants in exact interval
```

It is not:

```text
no provider row was returned
```

### 9.2 Paper included model

A Paper model that simulates funding events must emit `INCLUDED` and aggregate the deterministic model events whose event times belong to the exact interval.

No network/provider credential is needed for this local Paper model.

Paper funding model success remains Paper evidence only and cannot be relabeled as provider/live funding truth.

## 10. Stable identity and idempotency

`funding_evidence_id` is deterministic over canonical **allocation identity material**.

Normative identity material includes exactly:

```text
schema_version
funding_evidence_profile_version
source_kind
source
source_version
source_material_hash
source_record_count
source_complete_through
trade_plan_id
position_id
symbol
interval_start
interval_end
interval_semantics
status
funding_cost
cost_currency
```

`calculated_at` is audit observation metadata and is not part of the allocation identity hash.

Canonical identity algorithm:

1. serialize the identity material as UTF-8 JSON;
2. field names sorted lexicographically;
3. compact JSON separators;
4. decimal/time fields already normalized to their canonical strings;
5. compute SHA-256;
6. prefix the lowercase hexadecimal digest with:

```text
fundev_
```

Therefore:

```text
same immutable allocation identity material -> same funding_evidence_id
any identity-bearing material change         -> different funding_evidence_id
```

Implementations must never use random UUID generation for the canonical evidence identity.

### 10.1 `calculated_at` replay rule

Once one canonical evidence object is emitted/persisted, retries should replay that object rather than manufacture a new timestamped financial fact.

If the exact same allocation identity material is observed later with only a later `calculated_at`, it is duplicate observation metadata, not a new financial allocation. E6 must not overwrite the immutable first canonical object merely to refresh `calculated_at`; a later audit-observation log may be stored separately.

## 11. Duplicate and conflicting evidence behavior

Define the one-position allocation lineage key:

```text
(
  funding_evidence_profile_version,
  trade_plan_id,
  position_id,
  symbol,
  interval_start,
  interval_end,
  interval_semantics
)
```

Rules:

- repeated delivery of the same `funding_evidence_id` and identical identity material is idempotent;
- the same `funding_evidence_id` with different identity material is invalid/corrupt and fails closed;
- two different valid evidence IDs for the same lineage key mean authoritative source material changed or conflicts;
- conflicting evidence is never last-write-wins;
- E5 must not finalize a new TradeResult while conflicting evidence for the same lineage key is unresolved;
- E6 persists the conflict/audit trail but does not choose which financial truth wins;
- once a durable TradeResult references a funding evidence ID, later conflicting evidence must not silently mutate that TradeResult; correction/reconciliation requires an explicit later versioned policy outside V0.1.

This rule intentionally favors reconciliation over silent financial-history rewriting.

## 12. Fail-closed validation matrix

The following conditions cannot produce a final TradeResult:

| Condition | Required behavior |
|---|---|
| source unavailable / query failed | no final FundingAllocationEvidence; block finalization |
| source/version unknown to consumer | reject evidence |
| `source_complete_through < interval_end` | reject as incomplete |
| `calculated_at < interval_end` | reject as premature |
| interval not exact TradeResult interval | reject |
| interval overlap/approximation instead of exact interval | reject |
| position mismatch | reject |
| trade-plan mismatch | reject |
| symbol mismatch | reject |
| unsupported interval semantics | reject |
| unsupported currency | reject |
| malformed / NaN / infinite funding cost | reject |
| `ZERO_CONFIRMED` with nonzero cost | reject |
| `ZERO_CONFIRMED` with source records | reject |
| `INCLUDED` with zero source records | reject |
| same ID with changed material | reject as corrupt/conflict |
| different IDs for same lineage key | reconciliation conflict; no finalization |
| missing evidence | block finalization; never infer zero |

Unknown required enum/profile values fail closed.

## 13. Producer / consumer / persistence ownership

### 13.1 E4 — authoritative source acquisition and canonical producer

**Next implementation owner: E4.**

E4 owns actual broker/account execution truth and the PaperBroker/provider adapter boundary. Funding ledger/model facts belong with that execution/account source authority, not E5 risk policy and not E6 persistence.

A bounded later E4 task should implement a provider-neutral funding evidence source port or equivalent E4-owned composition surface that:

```text
exact closed position lineage + exact interval
-> versioned Paper model or authoritative broker funding source
-> complete normalized source material
-> funding-allocation-v0.1 FundingAllocationEvidence
```

E4 may reject/unavailable when completeness cannot be proven. It must not manufacture E5 lifecycle/risk semantics.

For current Gate B Paper work, the first producer should be local Paper-only and require no provider credentials/private APIs.

### 13.2 E5 — validator / consumer / TradeResult owner

E5 consumes the canonical shared evidence and validates exact:

```text
profile/schema
trade_plan_id
position_id
symbol
exact [opened_at, closed_at) interval
source/version support
completeness
status/cost/currency
conflict state
```

E5 does not query a provider merely to finalize a TradeResult and does not manufacture `ZERO_CONFIRMED`.

The current E5-private `FundingEvidence` helper may later be replaced or adapted internally, but no E4/E6 module may import it as the contract.

### 13.3 E6 — immutable persistence / replay / audit

E6 stores the canonical object, indexes its lineage/identity, restores it unchanged, preserves source metadata and detects duplicate/conflicting evidence according to section 11.

E6 must not:

- call a provider to fill missing funding;
- infer zero from missing rows;
- change cost/currency/status;
- recompute a new funding identity during restart;
- choose a conflicting financial truth by last-write-wins.

### 13.4 E7 — contract / compatibility / release authority

E7 owns this profile version, future compatibility changes, integration definitions and release-gate interpretation.

## 14. TradeResult consumption compatibility

For Gate B finalization after the funding producer/consumer follow-up is accepted, `trade-result-v0.1` must consume one exact valid `funding-allocation-v0.1` object.

The canonical evidence must bind exactly to:

```text
FundingAllocationEvidence.trade_plan_id == TradeResult.trade_plan_id
FundingAllocationEvidence.position_id   == TradeResult.position_id
FundingAllocationEvidence.symbol        == TradeResult.symbol
FundingAllocationEvidence.interval_start == TradeResult.opened_at
FundingAllocationEvidence.interval_end   == TradeResult.closed_at
FundingAllocationEvidence.interval_semantics == START_INCLUSIVE_END_EXCLUSIVE
```

Additive TradeResult audit references required for the current Gate B finalization path are:

- `funding_evidence_profile_version` — exactly `funding-allocation-v0.1`
- `funding_evidence_id` — exact consumed evidence identity

Existing fields remain:

- `funding_evidence_status`
- `funding_cost` for `INCLUDED` under the existing profile

Consistency rules:

```text
TradeResult.funding_evidence_status == FundingAllocationEvidence.status
```

For `INCLUDED`:

```text
TradeResult.funding_cost == FundingAllocationEvidence.funding_cost
```

For `ZERO_CONFIRMED`, effective funding cost is zero. Existing `trade-result-v0.1` may omit its `funding_cost` field or emit zero according to the existing accepted serialization rule, but it must retain the new evidence ID/profile references so zero remains auditable.

The accepted PnL formula does not change:

```text
net_pnl = gross_pnl - total_fees - funding_cost_effective
```

Legacy/static TradeResult objects without the new evidence references are not rewritten. They remain historical/static objects but are not current Gate B finalization evidence once this profile's producer/consumer chain is adopted.

### 14.1 Required later E5 adaptation

A bounded later E5 task must adapt `build_trade_result()` (or a shared validator boundary it consumes) to accept the canonical FundingAllocationEvidence shape and emit the two audit references above.

That adaptation must preserve all currently accepted fee, Decimal PnL, interval, lifecycle, identity and fail-closed semantics. This contract task does not modify E5 production code.

## 15. Persistence / restart / audit expectations

E6 later persistence must support at minimum:

- immutable storage by `funding_evidence_id`;
- unique/indexed lineage key from section 11;
- exact serialized profile/schema retention;
- exact source/source-version/source-material hash retention;
- exact interval/status/cost/currency retention;
- exact completeness watermark and calculated timestamp retention;
- idempotent replay of identical evidence;
- explicit conflict state when different evidence IDs share one lineage key;
- durable relationship from final TradeResult to the exact funding evidence ID;
- restart restoration without recalculation or semantic rewriting.

A TradeResult and its funding evidence are separate immutable audit objects. Deleting or replacing funding evidence referenced by a durable TradeResult is forbidden.
