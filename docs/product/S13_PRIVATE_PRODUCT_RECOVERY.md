# Private local product-data recovery

Implementation scope: master task / PLAT-09. Exact-clean full source and Windows native qualification are pending for this revision. Ubuntu service/reboot, upgrade with existing exposure and S12 continuous runtime commissioning remain separate acceptance gaps.

Stop all four native owner scopes before maintenance. `backup-product-data --config <profile> --destination <fresh-private-directory>` acquires control/research/runtime/cloud scopes and all present SQLite writer fences. The eight supported store locators include canonical, intake, queue, research, control commands, authentication, process supervision and control settings. SQLite backup reads committed pages and seals private copies without WAL/SHM sidecars.

The full bundle retains selected policy JSON, dataset manifests and actual hash-verified Parquet bytes without decoding sealed OOS, accepted package payloads and their independent `.seal.json`. It includes currently unselected imported dataset revisions. Capture streams bounded file chunks and repeats the source inventory/hash checks while owner/database fences remain held. The manifest is written last. Unknown durable files, links, duplicate paths, altered sources or incomplete coverage refuse a complete bundle. The exception reports a sanitized coverage gap, not private filenames or file contents. Known `worker-logs` and `process-scopes` roots are excluded without opening or enumerating their contents. Arbitrary cloud work roots/credential references are not implicitly excluded or read; an unfamiliar data layout must be reviewed before it is claimed covered.

`verify-product-backup --config <original-profile> --destination <bundle>` independently verifies profile, namespace/locator inventory, private permissions, exact file inventory, seals, actual byte hashes, database schema/integrity and the nested database-manifest commitment. No cloud publication is permitted. Backup bundles contain private owner data and password hashes and remain owner-private local artifacts; they are never performance feedback.

`restore-product-data --config <original-profile> --backup <bundle> --destination <fresh-local-generation>` refuses source/cloud/installation overlap, existing destinations or active owners. It preserves the source and stages a new private generation. `restored-product.json` binds the new local root and keeps cloud disconnected, diagnostic mode enabled and PAPER disabled. `restore-generation.json` is written last and binds a fresh UUID/time, backup identity and changed configuration.

Copied authentication sessions are revoked. Active intake leases and queued/running research leases are fenced; unfinished research attempts fail with retained reasons while completed evidence and holdout records remain unchanged. Actual E6 dispatch/PAPER process generations advance through their owning APIs. Positions, protections, uncertain provider claims, kill switches, reconciliation locks and committed effects remain facts requiring reconciliation; restoration produces no flat-position or provider-success claim.

Restoration consumes the exact bounded validated database manifest snapshot. Mutable rereads cannot supply a different output path; every destination must remain inside the fresh generation. An owner-private in-progress indicator is written before copying any data. A partial generation refuses owner startup even when an independently supplied configuration points at it before a restored profile or ready marker exists.

Authenticated health exposes `RESTORED_INHIBITED`, reconciliation REQUIRED and reauthorization REQUIRED. Repeated control/research restarts do not clear the marker. Incomplete or changed restored profiles cannot start owners. The full runtime composition must consume this fence and actual fresh release/preflight/reconciliation/approval evidence before any later exposure; that integration and qualification remain pending. There is no automatic resume command.

Complete inhibited product-data generations support subsequent private backups. The exact safe source-restoration identity is retained in the backup manifest; each later restore generates its own progress marker, profile and UUID. A database-only generation with missing user-data coverage cannot be relabelled as complete by backing it up again.

Monotonic deadlines apply to streamed copies, manifest/inventory verification, SQLite queries/integrity and each owning financial generation update. SQLite progress handlers and bounded busy waits stop database work; every committed generation is followed by a deadline check. A deadline failure retains an inhibited partial generation without a ready marker. These are software bounds; filesystem/kernel stalls are not a hard OS quota guarantee.

`backup-databases`, `verify-database-backup` and `restore-databases` preserve the narrower seven-store database-only interface. Its restore marker explicitly says DATABASES_ONLY and user-data restoration PENDING. Use the full product-data interface for supported local research profiles; never label a database-only copy as a complete data-root recovery.
